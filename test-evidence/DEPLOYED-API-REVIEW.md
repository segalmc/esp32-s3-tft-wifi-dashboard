# S3 deployed API and safety-gate investigation

## Findings

Two independent causes explain the supplied tablet runtime diagnostics:

1. **Deployed API/source mismatch.** Current `include/BoilerWebApi.h:73` unconditionally creates `heating` for a successful authenticated status response, irrespective of control gate or session activity. `src/BoilerWeb.cpp:208` fills its fields. The committed predecessor, HEAD `8969397`, lacks those fields entirely; its command handler also only accepts one argument, rejecting Android's three-field action/durationSeconds/targetC request. The heating-session additions are present as uncommitted working-tree changes. The existing FINAL-REPORT explicitly records that they were built offline and never flashed. The reported running API therefore does not expose the Android heating contract and is consistent with the predecessor firmware, rather than the current implementation.

   Exact deployed binary revision/hash is **not independently verified**. The API has no exposed build fingerprint, an attempted GET of the configured S3 endpoint `PRIVATE_DEVICE_IP/api/status` was blocked before connection by socket EPERM, and no `/dev/serial/by-id` devices were available. No serial port was opened, login/session replaced, or device rebooted. Runtime values in this report come from the user. A wrong controller endpoint or another older build cannot be excluded by a binary identity check here.

2. **Intentional control authorization is closed.** `include/BoilerWebPolicy.h:41` rejects ON/OFF availability when controlGate is false. That supplied false flag is sufficient to explain available.on=false, independently of Tuya connection, fresh OFF and clock synchronization. Other ON prerequisites still include online/read authorization, no busy command, fresh confirmed OFF, no outstanding lease, valid synchronized time and storage readiness. Their exact runtime values are not all supplied, so enabling one flag cannot be assumed sufficient.

   `include/BoilerPolicy.h:93` deliberately boots with control=false while persisted monitor authorization can restore reads. `src/TuyaControl.cpp:120` supports control authorization only through the USB enable path, requiring an armed monitor and enabled reads. `src/NetworkManager.cpp:435` handles that explicit USB command. Authentication and read access never grant physical control. The evidence does not establish whether authorization was never enabled or was cleared by a reboot; both produce the observed state. No authorization was changed.

Current source supports the heating API: authoritative status, paired duration/target settings, verified NVS lease before one ON attempt, fresh boiler-temperature shutdown, monotonic/reboot deadline handling, latched OFF retries and verified lease removal. The physical ceiling remains 1800 seconds; 45/60-minute operation is rejected. A cosmetic heating object in the old status API alone would not implement this contract.

## Verification performed

- Compiled the committed and working-tree serializers against identical in-memory OFF/fresh/read-authorized/control-disabled fixtures. HEAD: heating_present=false, available.on=false; worktree: heating_present=true, available.on=false. A policy-only fixture confirms that the control flag alone blocks otherwise-eligible ON. These are host fixtures, not device writes (`api-review-source-comparison.log`).
- PASS: 27 production TuyaControl host scenarios (`api-review-controller-tests.log`), plus session/deadline/preset/recovery and boiler/DPS/auth/CSRF/gate tests (`api-review-policy-tests.log`). These cover closed boot gates, persistence failures, uncertain ON without resend, OFF retries, stale temperatures and 45/60 restrictions.
- Both existing TFT USB/OTA firmware.bin files still match `build-artifact-hashes.json` and the previously successful build report. This fingerprints local artifacts only, not the running device. No rebuild/upload was required for this read-only review.
- Direct HTTP check blocked by socket permissions (`api-review-http.log`). No real relay request was sent.

## Required work and safe deployment plan

1. No new heating implementation or gate relaxation is needed to explain this fault. Review the existing complete changes together: HeatingSessionPolicy/BoilerPolicy, TuyaControl header/source, BoilerWebApi/BoilerWeb and main.cpp telemetry snapshot wiring. Keep stable communications and original ESP32 unchanged. Optional future improvement: expose a read-only build ID/API version; not implemented in this investigation.
2. Before any approved upload, independently verify the S3 identity, physical relay OFF and absence of any outstanding heating/shutdown lease; stop if uncertainty remains. Preserve NVS, monitor authorization, Wi-Fi/Tuya/dashboard/OTA credentials and existing recovery obligation. Do not erase or silently clear a lease.
3. Review the final source diff and focused test results, then build the chosen TFT USB/OTA environment without upload. Verify the S3 16-MB board, default_16MB partition layout, exact local firmware digest, matching credential configuration and USB recovery path. Confirm authenticated OTA settings if that route is selected. PlatformIO defaults to OTA, so do not invoke a generic Upload action while only preparing artifacts. Obtain explicit approval identifying the image, target and deployment method before flashing.
4. After approved deployment, use authenticated GET status only: verify the entire heating object exists even while inactive/control-disabled; physicalMaxSeconds=1800; existing relay/temperature freshness and availability remain honest; and the timer/deadline do not become a new session. Expected controlGate remains false after reboot, so Android ON remains disabled. Recheck authentication/CSRF, temperature-staleness behavior and passive ESP-NOW/Wi-Fi stability. Never send a trial ON, including an oversized duration, to production for validation; duration rejection is checked offline or on an isolated bench.
5. Physical control authorization and live relay/session tests remain separate explicit decisions. Do not automatically enable control or issue ON after flashing. Later bench tests should cover timer/target OFF, network/sensor loss, NVS reboot recovery, uncertain commands and verified OFF; any real actuator test needs separate specific approval. Rollback requires verified OFF/no outstanding lease, preservation of NVS and a reviewed compatible image.

Only evidence/report files were added in this investigation. No firmware source, credentials, safety gates, network code, original ESP32, installed image or physical relay was changed.
